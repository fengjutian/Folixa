# 版本与任务管理规范

## 1. 核心规则

本项目采用“一项主要任务对应一个软件版本”的开发方式：

- 每个版本只解决一个明确的主要问题。
- 每个版本必须有独立版本文档。
- 版本文档同时是需求、实现计划、验收清单和发布记录。
- 当前版本未通过验收，不开始后续版本的功能开发。
- 修复当前任务验收过程中发现的问题，不另起版本。
- 已发布版本出现独立缺陷时，使用补丁版本修复并创建对应文档。
- 软件中展示的版本号、CMake 项目版本、安装包版本和版本文档必须一致。

## 2. 版本号

采用语义化版本：

```text
主版本.次版本.补丁版本
```

- `0.x.0`：达到 1.0 前的计划任务版本。
- `0.x.y`：已完成任务版本的缺陷修复。
- `1.0.0`：首个满足正式发布质量标准的版本。
- `1.x.0`：1.0 后新增的独立产品任务。
- `1.x.y`：对应版本的缺陷修复。

任务版本使用带 `v` 的 Git 标签，例如 `v0.3.0`。程序内部使用不带 `v` 的版本号，例如 `0.3.0`。

## 3. 状态

每个版本只能处于以下状态之一：

| 状态 | 含义 |
|---|---|
| Planned | 已规划，尚未开始 |
| In Progress | 正在实现，当前只能有一个版本处于此状态 |
| Verification | 实现完成，正在构建、测试和验收 |
| Released | 已满足全部发布条件并建立 Git 标签 |
| Blocked | 存在已记录且无法在当前条件下解决的阻塞 |

## 4. 版本文档要求

每个版本文档必须包含：

1. 唯一主要任务。
2. 用户价值。
3. 范围内和范围外事项。
4. 设计决策。
5. 实施步骤。
6. 验收标准。
7. 测试要求。
8. 安全与隐私检查。
9. 依赖和许可证变化。
10. 风险及回滚方案。
11. 完成记录和已知问题。

## 5. 发布门禁

版本进入 Released 前必须满足：

- 版本文档中的验收项全部完成。
- Debug 和 Release 构建成功。
- 当前版本要求的自动化测试通过。
- 没有未说明的高严重度安全问题。
- 新增依赖已记录版本、来源和许可证。
- 用户可见变化已写入版本文档。
- 软件版本号与文档一致。
- 创建不可变的 Git 标签。

## 6. 变更控制

如果实现中发现任务范围过大，应在开发前拆成新的后续版本，不在当前版本中静默扩大范围。紧急安全修复可以插入补丁版本，但必须记录受影响版本、风险、修复和验证证据。

版本规划索引位于 [versions/README.md](versions/README.md)，新版本从 [版本模板](versions/TEMPLATE.md) 创建。
