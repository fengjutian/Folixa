# 对标基线：Foxit PDF Editor 2026

**基线冻结日期：** 2026-11-13  
**基线对象：** 本机安装的 `Foxit PDF Editor 2026.1.2.36547`（Continuous 通道，2.81 GB，3737 个文件，73 个插件模块）

本文是 1.x 全部版本的验收依据：**先定义"和谁比、比什么、怎么算赢"，再拆版本**。版本文档只描述怎么做到，不重新定义目标。

## 1. 对标口径

### 1.1 为什么拿编辑器当基线

免费版 Foxit Reader 只覆盖阅读与轻批注，用它对标会把目标定得太低。真正的用户预期是"打开 → 读 → 改 → 签 → 发"整条链路，这条链路只有编辑器版本才完整。所以基线取编辑器，阅读能力只是它的子集。

### 1.2 明确不追的四类

对标不是抄功能清单。以下四类**不作为目标**，理由写在评分卡的"不做"行里：

| 不追的对象 | 理由 |
|---|---|
| 企业内容管理（iManage / Documentum / SharePoint / Alfresco 等 8 个连接器） | 销售驱动型集成，需要目标客户与法务投入，与产品能力无关 |
| 插件 SDK 与第三方 `.fpi` 生态 | 十年的 ABI 与第三方积累，单人项目无法形成正循环 |
| 云文档、协同审阅、移动端与 Web 端 | 需要服务端与多端团队；本项目以本地优先为差异点，反着做 |
| 3D / 多媒体 / 作品集（Portfolio） | 使用率极低，且需要额外的渲染引擎与解码器 |

### 1.3 评分规则

每项能力有四个状态：

| 状态 | 含义 |
|---|---|
| 已具备 | 0.11.0 之前已经交付并通过验收 |
| 对齐 | 与福昕同一水平：功能在、结果一致、无明显降级 |
| 超越 | 福昕做不到或明显更差，且我们能量化证明 |
| 不做 | 明确排除，必须写明理由（见 1.2） |

三条硬规则：

- **R1**：标为 `Must` 的能力不得出现在"不做"里。降级为"不做"必须改本文并说明。
- **R2**："超过福昕"的判定 = 全部 `Must` 达到"对齐"及以上 + 第 4 节的翻盘点至少 5 项成立 + K 类（性能与兼容）不回退。
- **R3**：每一项必须有可执行的验收方式（自动化脚本、单元测试或人工核对清单）。**写不出验收方式的条目，不进入评分卡**——否则它只是一句愿望。

### 1.4 权重

- `Must`：缺了这条链路就断（打印、表单、签名、加密、批注互操作……）。
- `Nice`：有更好，没有不影响主流程（图层、PDF→Office、本地模型……）。

## 6. 风险

- **把对标做成抄清单**：功能逐条实现但体验割裂。对策：每个版本必须有"一条用户任务从头走到尾"的端到端验收，而不是散点功能。
- **长尾兼容性被低估**：福昕的护城河是二十年畸形文件、字体、XFA、打印驱动的脏活。对策：2.0.0 前建立 1000 份兼容语料并纳入 CI 抽样。
- **编辑引擎（1.11.0）拖垮节奏**：内容流编辑是唯一可能做不完的版本。对策：1.9.0 结束时做一次 go/no-go 评审，不达标就把 1.11.0 拆成"只读结构分析 → 文本行编辑 → 对象编辑"三段。
