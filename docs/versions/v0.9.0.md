**状态：** Released

## 用户价值

文档可以被快速检索，并为后续 AI 回答提供可定位的证据片段。

## 范围

- 文本块、章节路径、页码和坐标数据模型。
- 本地索引（落盘、检索、按页增量重建）。
- 索引面板：状态、取消、检索、结果定位与高亮。
- 范围外：向量检索和模型调用（留给 v0.10.0 / v0.11.0）。

## 设计决策

### 为什么不用 SQLite 与 FTS5

原计划是「SQLite 元数据 + FTS5 全文索引」。两个探针把它否掉了，
所以改成了自建的 JSON 索引 + 子串检索。

**探针一：Qt 的 SQLite 驱动在本工具链上加载即崩**
（`build/probe/sqlite_probe/`，C++/Qt）。

- `QSqlDatabase::addDatabase("QSQLITE")` 直接崩：0xC0000374（堆损坏），
  崩溃点在 ntdll。
- `QPluginLoader` 报 "Unknown error"；`plugins/sqldrivers/qsqlite.dll` 确实存在，
  但加载即崩。
- 用 `windeployqt` 把运行库部署齐了仍然崩——不是缺依赖的问题。

**探针二：FTS5 的默认分词器查不到中文**
（`build/probe/fts_probe.py`，Python 3.45.1 的 SQLite）。

| 查询 | 分词器 | 命中 |
|---|---|---|
| `人工智能` / `智能` / `文档检索` | `unicode61`（默认） | **0 行** |
| `index` | `unicode61` | 1 行 |
| 三字以上的词 | `trigram` | 能查到 |
| 两字词 | `trigram` | **查不到**（trigram 有 3 字下限） |

`unicode61` 按空格和标点切词，中文连成一整段就等于一个「词」，
所以除非整句完全一致，否则永远匹配不上。`trigram` 能救，但两字词失效——
中文里两字词（人脸、表格、索引）太常见，这个代价不能接受。

**探针三：倒排索引在这个规模下没有必要**
（同上脚本）：1000 段 × 220 字的子串扫描只要 **0.1 ms**。

### 结论：自建索引，后端可换

- 检索用**子串匹配**（忽略大小写）：中文直接能搜，不用分词；
  代价是扫全文，但实测在这个规模上完全可以接受。
- 索引存成**本地 JSON 文件**（应用数据目录下的 `index` 子目录，
  可用 `AIPDF_INDEX_DIR` 改位置），一个文档一个文件。
- 索引的**读写接口是独立的**（`LocalIndex`）：以后要换成 SQLite 或向量库，
  换的只是这一个类的内部实现，界面与分块器不用动。

### 坐标约定

索引里的坐标存 **PDF user space**（左下原点、单位是点），
与 `TextChar.box`、链接矩形是同一套。理由：索引是**文档自己的属性**，
不该随窗口缩放或用户旋转而变。要画到屏幕上时由 app 层用 `PageTransform`
转成显示空间（页面自带 `/Rotate` + 用户额外旋转）。

`PageTransform` 的旋转只用于**算行**（按视觉位置聚行）；
块的坐标存原始 user space，这样页面被旋转时索引不用重建。

### 增量：按内容指纹复用

每一页记一个「内容指纹」：**文本 + 页面盒子 + 文本整体包围盒** 的 SHA-1。

三者都要有，缺一个就会把「坐标不同」的页当成同一页：

- 文本变了，最明显的一种变化；
- 页面盒子变了（尺寸或位置），字符坐标就变了；
- 文本在页上的位置变了（同样的字排在不同地方），坐标也不一样。

重建时按指纹找回旧页：**内容没变就整页复用，只改页序号**。
所以在文档前面插一页，后面的页码整体后移也不用重建索引。

块的 id 用**内容指纹前缀 + 页内块序号**（如 `a1b2c3d4b0`），
与内容绑定而不是与页码绑定：页码变了 id 也不变，外部引用（搜索结果、
将来的引用出处）不会错位。

两页内容完全一样时 id 会重复，所以**定位一律带页号**
（`chunkByIdOnPage`），按 id 全局取会拿到另一页的块，坐标就错位了。

### 标题层级

标题靠**字高相对正文的大小**认（不靠字号，也不用模型）。

正文字高取**按字符数加权的行高中位数**：一页上往往只有一两个大标题，
普通中位数会被标题带走（「标题 18pt + 正文 14pt」的普通中位数是 18，
正文就被当成了标题）；按字符数加权之后，谁的字符多谁说话权重就大。

正文高度要**全篇统一**，标题层级才跨页一致。做法是先探前 8 页估出正文字高
（抽文本是最贵的一步，探的时候把文本与行缓存下来，主循环直接用），
并把这个值存进索引文件，下次重建直接复用。

层级映射：字高比 ≥ 2.0 → 1 级，≥ 1.6 → 2 级，≥ 1.35 → 3 级，
≥ 1.25 → 4 级，其余算正文。阈值比较留了 1e-6 的余量：
字高是从字符盒量出来的，卡在边界上不该抖。

### 分块规则

规则都是可解释的（界面验收按同样的规则断言）：

1. 行距 > 1.6 × 正文行距 → 换块（段落之间空了一行）；
2. 缩进变化 > 6 pt → 换块（列表项、引用块）；
3. 字高 ≥ 1.25 × 正文字高 → 标题块，层级由字高比决定；
4. 块 > 800 字 → 按行切开；
5. 非标题块 < 40 字 → 并进相邻块。

## 安全与隐私

- 索引默认仅本地保存（应用数据目录），可用 `AIPDF_INDEX_DIR` 改位置；
  删除该目录即彻底清除。
- 索引里只有从 PDF 文本层抽出的文字与坐标，不含批注、不含修改历史。

## 风险与回滚

- 风险：排版特征切出来的块不一定符合语义（哪句是「结论」是模型的事，
  本版只保证块内文字与坐标准确）；扫描件没有文本层，切不出块。
- 回滚：恢复至 `v0.8.0` 并删除索引工作区。

### 被测试抓出的缺陷

1. **总页数上报时机错了**：后台线程在接到任务之前就把总页数报给主线程，
   而主线程 `startIndexing()` 会把总页数清零，于是进度显示成「索引中 0/0 页」，
   轨迹里的页数也是 0。CI 验收断言 `index done ... pages=2` 时抓出来的。
   改成接到任务之后再报（队列保证顺序）。
2. **验收脚本对空列表的误判**：Qt 对**空的** `QListWidget` 不生成可访问接口，
   它不出现在 UI Automation 树里，所以面板刚打开时按 AutomationId 查
   `indexResults` 必然找不到。改成列表有内容之后才查。
3. **阈值比较的浮点抖动**：字高比正好落在 1.6 上时，二进制浮点算出来是
   1.5999999999999999，标题层级被判成低一级。阈值比较加了 1e-6 的余量。

### 已知限制

- 扫描件没有文本层，切不出块。
- 分块只按排版特征切，不做语义判断：哪句是「结论」是模型的事（v0.10.0 之后）。
- 检索是子串匹配，没有倒排索引：这个规模实测够用（1000 段扫描 0.1 ms），
  但文档规模再涨一个量级要重新评估。
- 索引只覆盖文本层与坐标，不含批注、不含修改历史；删掉索引目录即彻底清除。
- v0.8.0 遗留：移动页会打断该页内部链接与指向该页的链接（PDFium 159 无公开
  接口可修），本版未改动。
