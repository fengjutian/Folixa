# v1.3.0 — PDF 写入层与外观流

**状态：** Planned  
**唯一主要任务：** 建立可复用的 PDF 对象写入层，并为批注生成合规外观流（对标项 C10、I2）。  
**前置版本：** v1.2.0

## 用户价值

本程序写出的批注，在福昕、Acrobat、浏览器里都能看见，样子和本程序里一致；扫描件的 OCR 文本也能写回文档，成为真正可搜索的文本层。

## 范围

### 范围内

- 引入 PDF 对象层，提供增量更新与全量重写两种写入模式。
- 统一写入口 `DocumentWriter`：所有落盘路径（保存、另存、扁平化、盖章）都经过它。
- 外观流（/AP）生成器：高亮、下划线、删除线、方框、墨迹。
- 批注写入改为"字典 + 外观流"双写。
- OCR 隐藏文本层回写（不可见文本，`Tr 3`）。
- 写后校验与失败回滚。

### 范围外

- 加密、签名（1.6.0 / 1.7.0）。
- 内容流编辑（1.11.0）。
- 自研 PDF 解析器。

## 设计决策

### 为什么必须引入对象层

现状是硬约束，不是"还没写"：

- `FPDFAnnot_SetAP` **只写字典项，不创建 XObject**（PDFium 头文件明说），所以新建批注没有外观流；
- PDFium 只会渲染带 `/AP` 的批注，于是我们只能应用层自绘——**别的阅读器里这些批注是不存在的**；
- `FPDF_SaveAsCopy` 只有全量写，没有增量更新，也没有"新增一个 Form XObject"的公开接口。

没有对象层，C10（批注互操作）和 I2（文本层回写）都做不了，后面 1.5 的扁平化、1.6 的加密、1.7 的签名、1.11 的编辑同样做不了。这是整条路线的**地基**，必须先把地基做完，而不是在每个功能里各写一套半成品写盘代码。

### 地基验证结论（2026-11-14 实测）

写正式代码之前先做了一个一次性探针（`build/probe/ap_probe.cpp`，未入库）：拿 `annotation.pdf`，
用 PDFium 建一条 200×18 的 Highlight，再手写增量更新把 `/AP` 补进去。四条结论：

| # | 结论 | 影响 |
|---|---|---|
| 1 | `FPDFPage_GenerateContent()` **不生成** `/AP`（前后保存都没有 `/AP`，渲染差异 0） | 项目原有判断成立，"PDFium 能自己补外观"这条路可以彻底排除 |
| 2 | **PDFium 写出的批注是页面字典里的内联字典，不是独立对象** | 补 `/AP` 要重写**页面对象**；原以为改注释对象就够，实测踩中 |
| 3 | 手写增量追加可行：原 1223 字节一字未动，追加 602 字节，`startxref` 正确，重开后渲染差异**恰好 3600 像素 = 200×18，位置误差 0** | "自己实现对法层"的最低版本是成立的 |
| 4 | `/AP` 能被 PDFium 完整读回，并在全量重写中保留（二次保存后仍在） | 说明它是结构合法的对象，不是字节级障眼法 |

第 2 条直接改了设计，另外两条约束了实现：

- 写层必须**按对象重写 + 替换键**，不能追加键——否则重复保存会让页面字典里堆出多个 `/AP`；
- 每次编辑约 +600–700 字节，其中页面对象重写占大头：**增量链膨胀不是问题，被反复重写的是页面对象**，因此需要周期性全量压缩；
- 外观流对象要在重写时**复用同一编号**并管引用计数，避免每次编辑堆一个新对象。

**未验证**：福昕 / Acrobat 是否认这条 `/AP`。本机没有 qpdf、poppler、Ghostscript，LibreOffice 的
PDF→PNG 导出也没跑通，跨引擎确认只能人工看（`.tmp/ap_appended.pdf`，预期是页面中部一条
200×18 的半透明黄带）。**人工确认之前，C10 不算通过。**

验证之后已经把外观流生成器落地：`src/pdf/AppearanceStream.{h,cpp}` 覆盖高亮、下划线、删除线、
方框、墨迹、便签六种类型，13 条单测（`tests/AppearanceStreamTests.cpp`）全绿，并用临时补丁器
跑通了端到端（同一份 200×18 高亮，渲染差异 3600 像素、位置误差 0）。单测期间抓到并修掉一个
真实缺陷：坐标映射误用 Qt 的 `bottom()`（= y + height）当 PDF 下边界，会把多行高亮压成一行。

### 选 qpdf，不选 PDFHummus，也不自研

| 方案 | 结论 |
|---|---|
| 自研解析器 + 写入器 | 解析交叉引用流、对象流、增量链、损坏修复的边界情况极多，等于重做 qpdf，且没有测试语料 |
| PDFHummus（生成型） | 擅长"从零造一份文档"，改写现有文档时倾向于重建结构，会丢原始对象、破坏已有签名与线性化 |
| **qpdf（Apache-2.0）** | 对象级读写、增量更新、对象流、页面操作、加密都在同一套模型里；有 `--check` 可做外部校验 |

分工写死：**PDFium 负责渲染、文本、表单交互；qpdf 负责对象级写入；外观流的内容由我们自己生成**——外观必须和屏幕上像素一致，第三方库给不了这种一致性。

注意：验证结论（第 3 条）说明"不引 qpdf 也能做最基本的增量写入"。这不构成放弃 qpdf 的理由——
真实文件里批注是独立对象、还可能有对象流与加密，手写解析器撑不到 1.6 的加密与 1.7 的签名。
探针验证的是**路线可行**，不是**实现可以省**。

### 增量更新优先，全量重写兜底

- 增量：在文件尾部追加新对象与新的交叉引用，原有字节不变。好处是未改动部分（含已有签名覆盖的字节范围）不受影响，写盘也快。
- 全量：页面结构大改、需要清理无引用对象、或增量链太长（>32 段）时使用。
- 选择逻辑放在 `DocumentWriter` 里，调用方只说"我要改什么"，不说"用哪种写法"。

### 外观流生成器与屏幕绘制共用一份几何

外观流是一段 content stream：`BBox` 决定裁剪，`Matrix` 决定缩放，内容用 PDF 绘图操作符。它的坐标来自与屏幕绘制**同一个**几何函数（`annotationGeometry()`），否则"屏幕一个样、打印一个样、别人打开又一个样"。

生成后强制做三件事：`BBox` 必须覆盖全部内容（否则会被裁掉）、`/Resources` 必须声明用到的字体、`/Type /XObject /Subtype /Form`。

### 写后必须重开校验

沿用 v0.8.0 的安全保存：临时文件 → 用 PDFium 重新打开 → 校验页数、对象可解析、抽样文本一致 → 原子替换。**校验不通过就当没写过**，原文件与 `.folixa.bak` 保持原样。对象层出错的后果是文件打不开，这条不能省。

- [ ] 写入中途断电/进程被杀，原文件与备份不变，恢复日志可重放。
- [ ] OCR 文本层回写后，文档可被本程序与其他阅读器搜索到，且不显示可见文字。
- [ ] Debug 和 Release 构建成功。
- [ ] 自动化测试通过。
- [ ] 软件版本号与本文档一致。

## 测试要求

- 对象层：线性化文件、带对象流、带增量链、加密文件（只读）、损坏交叉引用。
- 外观流：旋转页、缩放页、裁剪页（CropBox ≠ MediaBox）、负坐标、超大 BBox。
- 回写：中文/英文/混排 OCR 结果，坐标映射误差 <1pt。

## 安全与隐私

- 对象层解析的是**不可信输入**：所有长度、偏移、对象编号必须做边界检查，禁止按文件内声明的大小分配内存。
- 解析失败一律回退到 PDFium 全量写，不允许"带病写盘"。

## 依赖与许可证

- 新增 `qpdf`（Apache-2.0），随包分发其许可证全文并登记到 `licenses/CHECKSUMS.txt` 与 SBOM。
- 这是本项目第一个源码构建的第三方依赖，需要同步修改 [依赖与许可证政策](../DEPENDENCY_POLICY.md)。

## 风险与回滚

- 风险：对象层 bug 直接损坏用户文件；增量链在多次保存后膨胀。
- 风险：**跨引擎兼容尚未验证**。PDFium 认这条 `/AP` 不等于福昕认；人工确认前不能宣称 C10 达成。
- 回滚：保留"只用 PDFium 全量写"的降级开关（外观流丢失但不损坏文件）；恢复至 `v1.2.0`。
