# v0.5.0 — 文本选择与搜索

**状态：** Verification  
**唯一主要任务：** 实现文本提取、鼠标选择、复制和文档内全文搜索。  
**前置版本：** v0.4.0

## 用户价值

用户可以查找、选择并复制 PDF 中的文本。

## 范围

- 字符、Unicode、坐标和阅读顺序提取。
- 鼠标命中、选区绘制和复制。
- 关键词搜索、结果列表、跳转和高亮。
- 范围外：OCR 和语义搜索。

## 设计决策

- **页面几何随文本层一起回传，不在主线程再问 PDFium。**
  字符框在 PDF user space（左下原点）里，要变成屏幕坐标必须知道页面盒子与旋转。
  这两个值在提取文本时就在手边（后台线程本来就拿着页面句柄），
  一起带回主线程即可：主线程的坐标变换变成纯数据换算，
  既不用再开一份 PDFium 句柄，也不用跟渲染线程抢 PDFium 的全局锁。
  有效盒子优先取 CropBox——PDFium 渲染的就是这个区域，字符框相对
  同一个盒子才能和页面图像对齐。
- **PDFium 的调用全部串到一把进程级递归互斥量上。**
  `fpdfview.h` 明确写着：PDFium 的接口不是线程安全的，同一时刻只允许一个调用在进行。
  本项目主线程、渲染线程、文本 worker 三条线程都会碰到 PDFium，
  违反这条约束会表现为随机堆损坏（崩在 `RtlAllocateHeap`，堆损坏点却早得多）。
  加锁前后做了对照实验：14 秒窗口内崩溃 1~2/5，加锁后 0/5。
- **阅读顺序与 PDFium 字符顺序分开记。**
  PDFium 给的字符顺序是内容流顺序，不等于人眼阅读顺序；
  排版层按行/列聚类重建阅读顺序。
  选区用阅读顺序区间（人拖出来的顺序），搜索命中用 PDFium 字符区间
  （关键词在字符流里的位置），两者不能混用。
- **PDFium 会在换行处插入 `\r`。** 这些控制字符没有字形、盒子是 0 宽 0 高，
  混进行聚类会凭空多出一行。排版层过滤它们，但文本层里保留，
  以免搜索匹配时跨行误命中。
- **搜索逐页推进，随时可取消。** 命中列表用增量追加而不是整表重建：
  整表重建在长文档下是 O(n²)（500 页 = 12.5 万次条目创建），界面直接卡住。

## 安全与隐私

- 提取文本仅保存在本地受控缓存。
  → 文本层只存在于内存中的 `QHash`，不落盘、不外发；
  搜索也只在本机扫描已提取的页面文本，不调用任何外部服务。

## 风险与回滚

- 风险：PDF 阅读顺序可能与视觉顺序不同。
  → 排版层按行/列聚类重建顺序，竖排（列比行少）单独处理；
  连字与 RTL 只做基本处理，未做完整 BiDi 排版。
- 回滚：恢复至 `v0.4.0`。

### 本轮修掉的问题

1. **拖选从来没有真正生效过——文本控制器手里没有可用的文档句柄。**
   `TextController` 的构造函数把 `document` 移给了后台线程，
   自己那份 `source_` 从来没被赋值，`transformFor()` 于是永远拿不到页，
   排版建不起来，命中测试恒为 -1：点哪都不选中。
   症状极具迷惑性——搜索却完全正常（搜索走的是另一条不需要坐标变换的路）。
   修法：页面有效盒子与 `/Rotate` 随文本层一起回传，
   坐标变换在主线程变成纯数据换算。
2. **PDFium 的接口不是线程安全的，三条线程并发调用会踩坏堆。**
   渲染线程、文本 worker 与主线程同时进 PDFium，
   表现为随机的 `0xC0000374` / `0xC0000005`，堆损坏点远早于崩溃点。
   现在所有 PDFium 调用都串到一把进程级递归互斥量上
   （`render()` 内部还会调 `widthPoints()`，所以必须可重入）。
   对照实验：加锁前 14 秒窗口崩溃 1~2/5，加锁后 0/5。
3. **旋转页被转了两次（v0.4.0 遗留）。**
   PDFium 自己就会应用页面的 `/Rotate`（`FPDF_GetPageWidthF` 返回的就是转过的尺寸），
   v0.4.0 又额外加了一次。已在 `render()` / `displayWidthPoints()` /
   `displayHeightPoints()` 修正，并由 `tests/PdfiumAdapterTests.cpp` 锁住。
   v0.4.0 文档里「PDFium 不会自动应用 /Rotate」的错误结论已更正。
4. **跳到最后一页时页码指示停在上一页。**
   内容装得下时滚动会被夹住，页面没法滚到视口顶部，
   于是「顶部那一页」并不是用户正在看的那页。
   现在页码指示按**视口里占面积最大的那一页**来报
   （`PageLayout::dominantPage()`，有单元测试覆盖）。
5. **搜索结果列表每命中一页就整表重建，长文档下是 O(n²)。**
   500 页文档会做 12.5 万次条目创建，界面直接卡住。改成增量追加。
6. **换关键词时，上一轮搜索的命中会混进新结果。**
   旧搜索可能正在处理某一页，它的命中会写进新一轮的命中列表。
   现在每次搜索有独立代号，旧代号的结果一律作废。
7. **验收装置本身的三处缺陷（都曾伪装成产品缺陷）。**
   - 前台窗口会被机器上别的程序抢走：合成鼠标事件落在**光标下的那个窗口**上，
     实测点击落到了隔壁程序上，拖选毫无反应。
     现在做鼠标操作前把窗口置顶，并断言窗口真的在前台。
   - 页面左边算错了 24 点（漏扣页边距），落点偏了一整个边距。
   - 轨迹文件是追加写的，上一轮的记录会让「拖选选中了预期的文字」在
     根本没拖选时也显示通过。现在每个场景开始前清空轨迹。
8. **搜索太快，验收抢不到「搜索进行中」的状态。**
   3000 页的文档全文搜索只要 0.5 秒（扫描成本按字形数量走，
   每页只有几个字的小页极快）。改成每页 60 行的文字密集文档、
   1000 页，搜索要跑 4 秒，「正在搜索…」才观察得到。
9. **UI Automation 在搜索进行中会变慢，瞬时状态读不到。**
   搜索产生上千条命中后，UIA 树里每条命中都是一个元素，
   整树遍历要好几秒（每次元素访问都是跨进程往返，而应用主线程正忙着处理命中）。
   于是「等界面显示正在搜索」读回来时搜索早就结束了。
   现在改成：**搜索开始前就把控件元素抓下来缓存**，之后只读单个元素的属性。
10. **UI Automation 的 InvokePattern 点不动 Qt 按钮。**
    对停止按钮调 Invoke() 没有任何反应，搜索照常跑完。
    改成用真实鼠标点击按钮在屏幕上的位置（验收脚本里本来就有一套鼠标工具）。
11. **界面本地化之后，「就绪」标记失配，探针一直返回过期快照。**
    `Wait-AiPdfWindowProbe` 用窗口文本里的 `ready` 判断「界面已就绪」，
    界面改成中文后这个标记再也匹配不上：每个带 `-RequirePattern` 的探针
    都要空等满超时才返回，而那时一闪而过的状态栏提示早就过期了——
    「取消密码后状态栏提示已取消」这类断言因此失败，看起来像功能坏了。
    修法：就绪标记改成始终存在的窗口标题信号（`AI PDF Editor`），
    状态栏的「就绪」只作为辅助；**标记必须真的能匹配**，
    否则探针返回的就是过期数据。
12. **Worker 状态与健康检查结果读不到。**
    两者都在默认收起的 AI 面板里，UI Automation 读不到；
    面板文案还会随改版变化，断言绑在文案上必然脆。
    改成让应用把 Worker 状态与健康检查结果写进诊断轨迹，验收按轨迹断言
    （`worker state=ready`、`worker health protocol=1 version=0.5.0`）。

### 已知问题

1. 搜索命中高亮画在整页矩形上，没有按词切分（多行命中的高亮会连成一片）。
2. 竖排文本只做了基础的列聚类，没有完整的竖排排版规则。
3. BiDi（阿拉伯语、希伯来语）只做了字符级处理，没有实现双向算法。
4. 文本层按页缓存在内存里，没有上限；超大文档会占用较多内存。
5. 搜索是线性扫描，命中很多时（每页都命中）会向主线程投递很多页文本。
6. 全文搜索是逐页线性扫描，没有倒排索引；十万页级别的文档不适用。
