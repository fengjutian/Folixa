## 1. 结论

计划中的 1.1 → 1.11 没有按顺序推进。实际代码集中在 **1.1–1.5、1.8、1.10，以及 1.11 的一部分**；
1.6 只落地了加密；1.7（签名）与 1.9（转换 / PDF-A）**完全没有开始**。
版本文档的“Planned”已经不能代表实现状态。

## 5. 发布边界：三个选项

### A. 直接发 1.0.0，之后重排 1.x

把 0.15.0 之后的能力视为 1.0 的组成部分，1.0 作为“质量里程碑”发布；
把未实现的 1.6 遮盖/1.7 签名/1.9 转换/1.10 无障碍/1.11 完整编辑重新编号到 1.x。

- 优点：立刻结束“版本号对不上代码”的状态。
- 代价：等于承认 1.1–1.8 的顺序计划作废，1.x 全部要重写；已发布的 0.x 语义也被跳过。

### B. 按原计划从 1.1 开始逐个收口（推荐）

先把 1.1 补完并发布，再按 1.2 → 1.11 顺序收口。1.2–1.5 的主体代码已经存在，
主要是补验收与文档；1.6 之后才需要新写。

- 优点：遵守“一个版本一个主要任务”“同一时间一个 In Progress”，历史可解释；
  1.1 只差一个验收脚本和 4 条断言，能很快拿到第一个 1.x 标签。
- 代价：1.6–1.9 的真实缺口（遮盖、签名、转换）会决定后面几个版本的节奏；
  已提前实现的 1.2–1.5 能力要以“验收补票”的方式进入对应版本。

### C. 发 0.16.0，把现状打包

保留 0.x，把 46 个提交记为 0.16.0。

- 优点：改动最小。
- 代价：0.x 已经承载不了当前能力面，且与 1.0 的发布目标越来越远。

**推荐 B。** 它不需要重写路线，也能把“文档说 Planned、代码已实现”的错位逐版本消化掉。

## 7. 横向问题

- **BOM 不一致：** `v1.1.0`–`v1.5.0` 带 UTF-8 BOM，`v1.6.0`–`v1.10.0` 不带。
  PowerShell 5.1 的 `Get-Content` 会把后者按 GBK 读成乱码（内容本身是合法 UTF-8）。
  建议统一加 BOM，或所有脚本显式 `-Encoding UTF8`。
- **验收脚本没有全部进 CI：** `verify-forms.ps1`、`verify-editing.ps1`、`verify-i18n.ps1`
  存在但不在 `ci.ps1` 的调用列表里。表单、编辑、国际化的界面验收没有进发布门。
- **对标进度已于 2026-11-16 重算两次：** 评分卡「已具备」43 → **46 / 95** → **52 / 95**，
  命令级对齐率 25% → **38%（104 / 276）** → **45%（125 / 276）**。两个数字都能引用了，但引用时带日期——
  再过一轮提交它们还会过期。
- **版本索引：** `docs/versions/README.md` 里 1.x 全是 Planned，与本审计冲突；
  在选定发布边界前先保留，选定后按版本逐个改。
