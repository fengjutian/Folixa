### 本轮推翻的**三条实现层面的判断**（都是审查与集成测试抓出来的，不是自查出来的）

| 既有判断 | 重算后的实际 |
|---|---|
| 「离线问答的引用粒度够细」 | **推翻**：`src/ai/OfflineQa.cpp` 切句时用 `QLatin1Char('。')` 判断中文句末标点，而 `QLatin1Char` 的参数是 `char`（单字节），多字符字面量被截断成 `0x82`，比较永远为假 —— **中文文档整段被当成一句话**，问「自动保存的间隔是多久」时引用指向整段而不是那一句。已改成按码点比较，并补了回归测试（退回修复后当场变红） |
| 「印前检查能扛住畸形文件」 | **推翻**：`src/pdf/PreflightChecker.cpp` 的对象图遍历是**递归**的，且 `inspectDictionary()` 给子节点写死深度 `1`，把 `kMaxObjectDepth` 守卫彻底废掉 —— 坏文件一条几千层的间接对象链就能爆栈（实测 chain=5000 时进程退出码 `0xC00000FD`），而印前检查已经接进界面。已改成**显式栈**遍历（堆上的栈没有深度上限），回归测试在旧实现上整个测试进程 SegFault |

### 这一轮抓到的实现层事实

- **Qt 6.8 的 `qUncompress` 要求输入前面有 4 字节大端长度前缀**，裸的 RFC1950 zlib 流会被判为损坏 ——
  PNG 的 IDAT 正是裸流。是先写探针实测才发现的（看文档看不出来）；
  同一次探针还确认了「截断的 zlib 流返回空 + 一条 warning，不会挂死」。
- **Ribbon 文案在英文界面下能翻译**：Qt 6.8 的 moc 生成的 context **带命名空间**
  （`aipdf::app::MainWindow`），与翻译目录里的 context 一致 —— 这一条是用 moc 输出复核过的，不是推断的。
- **私有构建目录必须显式带仓库的 toolchain**：漏掉 `-DCMAKE_TOOLCHAIN_FILE` 会挑到系统里的另一个 g++，
  与 Qt 官方 DLL 的 ABI 不合，**测试进程直接堆损坏 SEGFAULT（0xC0000374）**，连原样代码也崩。

### 1.8.4 2026-11-20 第二十四次盘点（不改数字：把文档级附件面板接回来）

上一轮盘点时发现一条**更硬的旧账**：「编辑 / 附件 / 文件附件」这条 partial 的说明列写着

README 里写着「等并行会话结束后恢复」——那个会话早就结束了，暂存区却一直没人碰。
这一轮把它接回来。

**接回来的东西**：

| 层 | 文件 | 内容 |
|---|---|---|
| 领域层 | `src/pdf/kernel/PdfiumAdapter.{h,cpp}` | `DocumentAttachment` 结构 + `attachments()` / `attachmentData()` / `addAttachment()` / `removeAttachment()`，走 PDFium 的嵌入文件接口（`fpdf_attachment.h`） |
| 界面层 | `src/app/panels/AttachmentPanel.{h,cpp}` | 三列表格（名称 / 说明 / 大小）+ 添加 / 打开 / 保存副本 / 删除 + 空状态 |

| 接线 | `src/app/shell/MainWindow.{h,cpp}` | 导航栏新增「附件」页（批注与表单之间），四个动作接到当前文档 |

**实测出来的三件事**（都是写代码时量出来的，不是推断）：

1. **PDFium 真的会把附件写进文件**：加 → 序列化 → 重开，附件还在，内容**逐字节原样**。
   这条走的是应用**真正的保存链路**（`pdf::DocumentWriter::save`，含外观流补写、
   qpdf 结构校验、重开校验），不是只测适配层的 `serialize()`。
2. **删除是真删**：删掉附件再存，文件体积**实测变小 262 554 字节**
   （载荷特意用固定种子的随机字节——全是 `'A'` 的载荷会被 Flate 压成几百字节，
   拿它比体积根本测不出「数据还在不在」，搜明文标记同样测不出来）。
   所以 PDFium 那个「删除只是从名字树上摘掉」的文档说法，在**本仓库的保存链路上不成立**。
3. **文档级附件带不了 MIME 类型**：PDFium 的嵌入文件接口只能把键写进 `/Params`
   （写出来是 `/Params<</#2FSubtype(text/plain)…>>` 这种非标准位置），
   够不到嵌入文件流的 `/Subtype`，它自己的 `FPDFAttachment_GetSubtype` 也读不回来。
   试过写 `/Subtype` 与 `Subtype` 两种键，都是同一个下场。
   → 结论：**别的阅读器只能靠文件名后缀判断这个附件的类型**。
   页面上的附件批注（`/FileAttachment`）另有一条路径——嵌入文件流由本程序自己写，
   那条**带正确的 `/Subtype`**。两条路径不是一回事，矩阵说明列分开写。

**矩阵那一行仍是 partial**（降级边界从「面板是空壳」换成「不带 MIME 类型」），
说明列按实情重写，评分卡 C8 的验收列同步。**数字不变**：仍是 223 / 276（81%）、
partial 24 条。

### 1.9 2026-11-20 第二十五次盘点（A6：集中的视图设置面板 + 页面布局按文件记住）

这一轮核的是矩阵里 A6「视图设置」那条 partial。它的说明列写着
「**没有集中的视图设置面板**，布局与侧栏可见性不记忆」——两件事，这轮两件都做了。

**做了什么**：

| 层 | 文件 | 内容 |
|---|---|---|
| 领域层 | `src/app/editor/ViewMemory.{h,cpp}` | `viewSettingsKey(path, group)`（键格式 `view/<group>/v1/<hash>`）+ `rememberedLayoutForFile()` / `rememberLayoutForFile()` |
| 界面层 | `src/app/dialogs/ViewSettingsDialog.{h,cpp}` | 缩放 / 页面布局 / 显示 / 视图旋转四组；面板里只列已经能用的能力 |
| 视图层 | `src/app/editor/PdfView.{h,cpp}` | `zoomFitsWidth()` / `zoomFitsPage()` / `userRotation()` / `rulerVisible()` / `setUserRotation()`；打开文档时恢复记住的布局 |
| 接线 | `src/app/shell/MainWindow.{h,cpp}` | Ribbon「视图 → 显示 → 视图设置」入口 |

**三件必须写清的事**：

1. **缩放的老键不能变**。缩放记忆的键算法搬到了 `ViewMemory`（缩放与页面布局属于同一族
   视图状态，键里带分组名，同族互不干扰），但键格式 `view/zoom/v1/<hash>` **一个字没改**——
   改了的话所有文件在升级后都会回到 100%，用户看不出原因，只觉得「记忆丢了」。
   `ViewSettingsTests` 里有两条钉住这件事：一条比两个函数给出的键相等，
   一条直接钉住键的**格式**（版本前缀一变就红；只比「两者相等」不够，两个函数一起改就又相等了）。
2. **面板里不列没有的能力**。福昕的视图设置里还有「隐藏批注 / 隐藏表单域 / 灰度显示 /
   显示裁剪框」这类开关，本程序没有这些能力，面板里就没有这一组——
   不列点不动的开关，也不编一个假的开关顶上去。
3. **缩放方式不从比例反推**。「适合宽度」和「实际大小」在某些窗口宽度下比例完全一样，
   反推会把「刚好 100% 的适合宽度」误判成实际大小。视图层自己记着当前是哪种适配模式
   （`zoomFitsWidth()` / `zoomFitsPage()`），面板读它。

**一处行为收窄**（不是新能力，是把话说准）：`PdfView::setZoom()` 现在明确指定比例时
**先清掉「适合宽度 / 适合页面」标志**。原先只在比例**变了**时才清，于是「刚好 100% 的
适合宽度」那种情形下点「实际大小」，比例没变 → 标志没清 → 面板显示还停在「适合宽度」。
这属于界面层行为，本轮没有专门的自动化用例钉住，靠人工验收。

**测试与负例对照**：

- 新增专项单测目标 `ViewSettingsTests` 7 条（对话框初值 / 读回 / 自定义百分比启用状态

- `ZoomMemoryTests` 5 条：缩放键算法搬走后，这个目标也要编进 `ViewMemory.cpp`

- **负例对照**（`build/negative-check-view-settings.py`，备份 → 改坏 → 重编 → 跑测试 →
  还原 → 复检；**每个负例之间先还原**，否则上一次的破坏会叠到下一次，红的用例数就说不清了）：
  弄坏键的版本前缀 → 键格式那条当场变红（1 条）；弄坏布局记忆读回 → 2 条变红；
  弄坏面板读回 → 读回那条变红（1 条）；弄坏自定义百分比的启用状态 → 那条变红（1 条）；
  四轮还原后复检全绿（QTest 报 Totals 9 = 7 条用例 + init/cleanup 各 1 条）。

## 5. 发布边界：三个选项

### A. 直接发 1.0.0，之后重排 1.x

把 0.15.0 之后的能力视为 1.0 的组成部分，1.0 作为“质量里程碑”发布；
把未实现的 1.6 遮盖/1.7 签名/1.9 转换/1.10 无障碍/1.11 完整编辑重新编号到 1.x。

- 优点：立刻结束“版本号对不上代码”的状态。
- 代价：等于承认 1.1–1.8 的顺序计划作废，1.x 全部要重写；已发布的 0.x 语义也被跳过。

### B. 按原计划从 1.1 开始逐个收口（推荐）

先把 1.1 补完并发布，再按 1.2 → 1.11 顺序收口。1.2–1.5 的主体代码已经存在，
主要是补验收与文档；1.6 之后才需要新写。

- 优点：遵守“一个版本一个主要任务”“同一时间一个 In Progress”，历史可解释；
  1.1 只差一个验收脚本和 4 条断言，能很快拿到第一个 1.x 标签。
- 代价：1.6–1.9 的真实缺口（遮盖、签名、转换）会决定后面几个版本的节奏；
  已提前实现的 1.2–1.5 能力要以“验收补票”的方式进入对应版本。

### C. 发 0.16.0，把现状打包

保留 0.x，把 46 个提交记为 0.16.0。

- 优点：改动最小。
- 代价：0.x 已经承载不了当前能力面，且与 1.0 的发布目标越来越远。

**推荐 B。** 它不需要重写路线，也能把“文档说 Planned、代码已实现”的错位逐版本消化掉。

## 7. 横向问题

- **BOM 不一致：** `v1.1.0`–`v1.5.0` 带 UTF-8 BOM，`v1.6.0`–`v1.10.0` 不带。
  PowerShell 5.1 的 `Get-Content` 会把后者按 GBK 读成乱码（内容本身是合法 UTF-8）。
  建议统一加 BOM，或所有脚本显式 `-Encoding UTF8`。
- **验收脚本没有全部进 CI：** `verify-forms.ps1`、`verify-editing.ps1`、`verify-i18n.ps1`
  存在但不在 `ci.ps1` 的调用列表里。表单、编辑、国际化的界面验收没有进发布门。
- **对标进度已于 2026-11-16 重算两次：** 评分卡「已具备」43 → **46 / 95** → **52 / 95**，
  命令级对齐率 25% → **38%（104 / 276）** → **45%（125 / 276）**。两个数字都能引用了，但引用时带日期——
  再过一轮提交它们还会过期。
- **版本索引：** `docs/versions/README.md` 里 1.x 全是 Planned，与本审计冲突；
  在选定发布边界前先保留，选定后按版本逐个改。
