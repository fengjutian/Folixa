## 本轮（第三十次）做掉的一项

这一轮补的是一条**输入格式能力**：TIFF（含多页 TIFF）。

| 项 | 原来的状态 | 现在 |
|---|---|---|
| TIFF 输入 | 领域层只认 BMP / JPEG / PNG，TIFF 明确报错「格式不支持」 | 自研 TIFF 解码器（`pdf::convert::TiffDecoder`）：大端 / 小端、灰度 1/2/4/8/16 位、调色板、RGB 8/16 位、压缩支持未压缩 / LZW / Deflate / PackBits；**多页 TIFF 按页展开成多页 PDF**，页序不变 |

关键取舍：

- **自研，不引 libtiff**。沿用仓库里 BMP / PNG 的自解路子（部署包实测只有 gif / ico / jpeg / svg
  四个 Qt 图像插件，用 `QImageReader` 在用户机器上会直接失败），也就不动依赖策略。
- **能明确报错的就不给半张图**。分块（tiled）、平面布局、JPEG-in-TIFF、CCITT、CMYK、
  BigTIFF、FillOrder=2 一律明确失败并说清原因。
- **拿真实文件对拍定标**，不靠自造字节自说自话。夹具由 libtiff（Pillow）写出并签进仓库
  （`tests/fixtures/tiff/`），解码器必须解出与 libtiff 逐像素一致的结果才算过。
  这一步很值：LZW 的「码宽增长门槛」差一格就会整条流错位，解出来是一整片噪点而且**不报错**，
  自造字节 + 自写解码器是发现不了的。

这条能力同时让两条用户路径受益：「图片转 PDF」（`pdf::imagesToPdf`）与「从扫描仪」
（`app::ScannerCapture`）——扫描仪本来就被点名要 TIFF 格式（WIA 的
`wiaFormatTIFF = {B96B3CB1-…}`），以前拿到的帧会直接报「格式不支持」。

## 本轮（第二十九次）已经做掉的三项

这一轮处理的是「后端早能做、界面没接出来」和「永远点不动的占位」——它们不是能力缺口，
是接线缺口，做完之后用户才真的用得上。

| 项 | 原来的状态 | 现在 |
|---|---|---|
| 静态 XFA 字段改值 | 后端能写值（`pdf::writeXfaFieldValues`），Ribbon 上的编辑入口是一个禁用占位 | Ribbon「表单 → 编辑静态 XFA」（`form.xfa`）接通：表格里改「新值」→ 点「写回文档」写进文档，逐项报成功与失败原因 |
| AI 快捷项「改写」「校对」 | 两个按钮永远禁用，提示「将在后续版本中提供」 | 两个都是真动作：新增 `ai::Task::Rewrite` / `ai::Task::Proofread`，作用于当前选区，走同一套 Provider 与隐私策略 |
| 编辑页附件组的「添加 3D」 | 一个永远点不动的禁用按钮 | 删除：3D 注解早就能写能读能渲染，真正的入口是「插入 3D 模型」与「查看 3D 模型」 |

三件事的共同点：**领域层能力本来就在，缺的是界面入口与状态口径**。
所以这一轮没有新增能力项，矩阵的 aligned / partial 数字不变。

## 建议继续开发的功能

### 1. 静态 XFA 的剩余边界（不是「没开发」，是范围之外）

静态 XFA 的字段提取、字段值改写、计算脚本子集执行都已实现，并且这一轮把值改写接到了界面上。
剩下的边界是**产品范围**上的，不是能力缺口：

- 动态 XFA 的脚本、事件与 SOM 运行时不做（界面在改值入口旁边写明了这一点）；
- XFA 的布局不做（只改值，不重建版面）；
- 界面验收脚本（`scripts/verify-forms.ps1`）目前只覆盖表单页签，**没有覆盖 XFA 编辑对话框**。

建议：给 XFA 编辑入口补一段界面验收（改值 → 写回 → 重新打开核对值确实变了）。

### 2. 补齐扫描仪兼容性和真机验证

当前扫描功能已经实现 WIA 设备枚举、取帧和多页 PDF 生成，但仍有以下边界：

- 只支持 WIA，不支持 TWAIN。
- 图像格式支持 BMP、JPEG、PNG 与 TIFF（TIFF 是这一轮补上的，含多页 TIFF 展开）；
  GIF / WebP 明确报「格式不支持」。
- 模拟帧源的自动测试已经通过，但扫描仪真机取帧尚未验证。

建议：

- 增加 TWAIN 支持，或明确维持 WIA-only 的产品范围。
- 建立至少一组真实扫描仪的验收环境。

### 3. 开发原生 OFD 读取与转换能力

当前 OFD 批量转换依赖用户自行安装外部转换器，应用本身没有 OFD 读取引擎。没有外部工具时，该能力不可用。

建议：

- 评估引入固定版本的 OFD 解析依赖，或开发最小可用的 OFD 读取层。
- 支持直接预览 OFD，而不仅是转换为 PDF。
- 保留现有外部转换器作为兼容或降级路径。

### 4. 完成 PDF 优化和 PDF/A 认证链路验证

PDF 优化的真实压缩路径依赖 Ghostscript；当前环境没有安装 Ghostscript，因此该路径尚未完整实跑。PDF/A 正式认证依赖 veraPDF，应用内置能力只能进行结构预检。

建议：

- 在 CI 或专用验证机安装并固定 Ghostscript 版本。
- 对压缩率、文字可搜索性、图片质量和逐页渲染差异建立验收门。
- 安装并固定 veraPDF，区分“内部预检”和“标准认证”。

### 5. 补齐高级打印的应用侧能力

双面打印、多页合一等能力目前取决于打印机驱动，应用侧没有统一实现和跨设备保证。

建议：

- 对多页合一进行应用侧排版和栅格化，减少驱动差异。
- 明确区分应用提供的打印能力和驱动提供的能力。
- 使用实体打印机和虚拟打印机进行组合测试。

### 6. 完成 OneNote 真机集成验证

OneNote 导出代码和自动测试已经完成，但依赖 Windows 上的 OneNote 桌面版与 COM。目前尚未验证真实写入以及 OneNote 中的文字搜索效果。

建议：

- 在安装 OneNote 桌面版的机器上执行端到端验收。
- 验证多页文档、中文文字层、特殊字符和大文档。
- 验证 COM 初始化失败、首次启动未配置和写入中断等场景。

### 7. 完成 AI 助手的真实 Provider 验收

AI 面板现在能做总结、解释、翻译、改写、校对与整篇问答（改写与校对是这一轮接上的，
两者都作用于当前选区，与「总结」作用于当前页不同）。但仍需真实服务验证模型响应格式、
流式输出、异常处理和兼容性。

建议：

- 为每个 Provider 建立最小在线冒烟测试。
- 验证流式输出、取消、超时、限流和错误响应。
- 演示模式下的改写与校对答复必须标明是本地拼的示例（已经这样标了），别让人误以为模型真的答了。

## 界面与实现状态不一致（本轮已消除）

### 「添加 3D」旧占位入口

以前编辑页附件组里有一个永远点不动的「添加 3D」按钮。项目早已存在可用的「插入 3D 模型」
与「查看 3D 模型」入口，功能矩阵也把 3D 标记为 `aligned`——那个按钮是早年的接线遗留，
留着只会让人以为 3D 能力没做。**这一轮已经删掉。**

### XFA 状态不一致

以前功能矩阵把静态 XFA 标记为 `aligned`，而 Ribbon 上的编辑入口却是禁用占位。
**这一轮接通界面后，矩阵与实现的口径一致（`aligned`）。**

## 明确不在产品范围内的功能

以下功能被登记为 `excluded` 或 `na`，属于产品决策，不应直接统计为开发遗漏：

- SharePoint、iManage、eDOCS 等企业内容管理连接器。
- 第三方插件 SDK、插件管理和插件商店。
- 云文档和云协作。
- 手机遥控。
- 商业激活、购买和订阅。
- 云端对内/对外电子签平台及邀请他人签署。
- CAJ 输入。
- 企业敏感度标签。

## 推荐优先级

1. 给 XFA 编辑入口补一段界面验收（改值 → 写回 → 重新打开核对）。
2. 增加 TWAIN，并完成扫描仪真机验证。
3. 建设原生 OFD 读取能力。
4. 完成 Ghostscript、veraPDF 的固定依赖与端到端验证。
5. 完成 OneNote 和 AI Provider 的真实环境验收。
6. 改进高级打印的应用侧排版能力。
